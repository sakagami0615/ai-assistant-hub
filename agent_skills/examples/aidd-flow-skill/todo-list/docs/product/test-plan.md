# テスト方針

## 戦略

`docs/product/specs/todo-management.md`を検証可能な振る舞いへ分解し、Docker Compose内のDjango標準テストランナーで自動化する。実装前に対象テストを書き、機能が存在しないことを理由に失敗することを確認してから最小実装を追加する。

## テストレベル

- モデルテスト: 既定ステータス、選択肢、表示文字列、並び順を検証する。
- フォームテスト: 有効なタイトル、空白のみ、最大長、前後空白の除去を検証する。
- ビューテスト: 一覧、追加、ステータス変更、削除、リダイレクトを検証する。
- HTTP境界テスト: 404、400、405、CSRF保護を検証する。
- テンプレートテスト: 空状態、ToDo、ステータス選択肢、フォームエラーの表示を検証する。
- コンテナ構成検証: Python 3.14、Djangoシステムチェック、マイグレーション状態を検証する。

## 検証対象

- 新規ToDoが未着手で保存されること
- 作成日時の新しい順で一覧表示されること
- 有効なタイトルを追加できること
- 不正なタイトルを保存せずエラー表示すること
- 3種類の任意のステータスへ変更できること
- 不正なステータスで現在値が変わらないこと
- ToDoを削除できること
- 存在しないToDoを適切に扱うこと
- 更新操作がPOSTとCSRFを要求すること

## 外部依存の扱い

- Djangoが作成する分離されたテスト用SQLiteデータベースを使用する。
- テスト、Ruff、Django管理コマンドは`docker compose run --rm web`経由で実行する。
- 通常実行時のSQLiteファイルは名前付きボリュームに保存するが、テストDBはコンテナ内で分離する。
- 外部API、ネットワーク、ファイルサービスは使用しない。
- 時刻そのものはモックせず、テストデータの作成順序または明示した日時で並び順を検証する。

## 非ゴール

- ブラウザを起動するE2Eテスト
- 負荷テスト、長時間テスト
- SQLite以外のDBに対する互換性テスト
- Django本体の機能の再テスト
