# decision-twin の学習フロー

ユーザーが「decision-twin で学習したい」のように学習を明示したときの手順。AI が題材を出してユーザーに1問ずつ質問し、回答を判断ノートに蓄積する。目的は、後の代理回答で根拠にできる判断を増やすこと。代理回答（twin-answerer / twin-verifier）は使わない。

ここで記録した判断は、本番のラウンドで答えた判断と同じ重みで扱われる。だから質問はユーザーの考えを引き出すことに徹し、AI の推奨で答えを誘導しない。

## 手順

### 1. 準備

1. `.decision-twin/` がなければ作る。`.gitignore` の提案は SKILL.md の手順1と同じ。
2. `docs/decisions/` の判断ノートと `docs/principles.md` を読み、既に決まっていることを把握する。
3. セッション番号を、`.decision-twin/log.jsonl` の `type: "learning"` 行の `session` の最大値 + 1 にする。

### 2. 題材を選んでもらう

1. 題材の候補を3〜5件出す。リポジトリの README、主要ディレクトリ、設定ファイル、依存関係から、このリポジトリで判断が必要になりそうな領域を選ぶ（例: 認証、一覧 API、DB マイグレーション、テスト方針）。
2. リポジトリが空、または題材を読み取れないときは、定番から出す: API 設計、DB、テスト、命名、エラー処理、ログ、依存ライブラリ。
3. 判断ノートに項目が多い題材は候補の後ろに回す。
4. ユーザーに1つ選んでもらう。候補にない題材の自由入力も受け付ける。

**完了条件:** 題材が1つ決まっている。

### 3. 1問ずつ質問する

1. 題材について、実装で実際に分かれ道になる判断を1つ選び、質問を作る。判断ノート・原則・リポジトリの事実で既に答えが出ている質問は出さない。
2. 質問には選択肢を2〜4件付け、自由回答もできると書く。推奨・おすすめの印は付けない。各選択肢の違い（何が変わるか）は1行ずつ中立に書いてよい。

   ```
   📝 **l-1-3** - **一覧のページング方式**（題材: API 設計）: 一覧 API のページングはどちらにしますか？

   1. offset 方式 — 実装が簡単。件数が多いと遅くなる
   2. cursor 方式 — 件数が多くても速い。任意のページへは飛べない

   番号か自由回答で答えてください。理由があれば一緒に書いてください。「終わり」で終了、「題材を変えて」で題材を選び直します。
   ```

3. 1問出したら、ユーザーの回答を待つ。AskUserQuestion が使えるなら使ってよい（推奨の印は付けない）。

### 4. 回答を記録する

回答を受けるたびに、次の質問を出す前に記録する。

1. 回答を判断ノートに出所 `学習` で書く。書き方は [recording.md](recording.md) の「判断ノートの書き方」。既にある項目を変える回答なら、その行を書き換えて `replaces` に元の id を入れる。
2. `.decision-twin/log.jsonl` に `type: "learning"` の行を1行追記する。形式は [formats.md](formats.md)。
3. 「わからない」「どちらでもいい」「今は決めない」という回答は判断ノートに書かず、log だけに `note: null` で残す。
4. 回答に一般化できる理由があれば、終了時の原則の追記案のためにメモしておく。

**完了条件:** その質問の log 行があり、記録対象の回答は判断ノートに書かれている。

### 5. 続けるか終えるか

- ユーザーが「終わり」と言うまで、手順3に戻って次の質問を出す。
- 「題材を変えて」なら手順2に戻る。
- その題材で聞くべき判断が尽きたら、そう伝えて別の題材を選ぶか終えるかを聞く。

### 6. 終了する

1. メモした理由があれば、原則の追記案をまとめて提示し、承認された文言だけを `docs/principles.md` に書く。手順は [recording.md](recording.md) の「原則の追記」。
2. このセッションで書いた・書き換えた判断ノートの項目を一覧にして伝える（題材ファイル、見出し、決めたこと）。

**完了条件:** セッションの全質問の log 行があり、原則の追記案が承認または却下されている。
