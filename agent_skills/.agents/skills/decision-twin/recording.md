# decision-twin の記録ルール

判断記録は「ユーザーが言ったこと」と「ユーザーが承認したこと」だけでできている状態を保つ。AI の推測だけで ADR や原則を書かない。

## log.jsonl

- 全質問について1問1行を追記する。形式は [formats.md](formats.md)。
- 追記だけを行う。既存の行は書き換えも削除もしない。集計の土台になるため。

## ADR を書く場面

| 場面 | source | supersedes |
| --- | --- | --- |
| エスカレーション質問にユーザーが答えた | `human` | 置き換える既存 ADR があればその id |
| 代理回答一覧の回答をユーザーが上書きした | `human` | 代理回答の根拠になった ADR があればその id |
| 一覧の `INFERRED` を承認した | `approved-inferred` | なし |
| 一覧の `PROPOSAL` を承認した | `approved-proposal` | なし |

次のものは ADR に書かない。

- `FACT` と `EXPLICIT_DECISION`（再調査・参照できるため）
- 保留した質問、承認されていない代理回答

矛盾（規則5）を解消する回答では、ユーザーが採らなかった方の ADR を `supersedes` に入れる。

## ADR の書き方

- 置き場所は `docs/decisions/`。既存の ADR があればその採番とファイル名の形式に合わせる。なければ `ADR-<3桁連番>-<英語ケバブケースの要約>.md`。
- テンプレートは [assets/templates/adr.md](assets/templates/adr.md)。既存 ADR の節構成が違うなら既存に合わせ、frontmatter の項目は必ず揃える。
- `owner` は `git config user.name`。`date` は記録した日。`scope` は影響範囲（`db`、`api/public` など）。
- 「理由」にはユーザーが述べた理由だけを書く。述べていなければ「（記載なし）」。
- 既存の ADR は編集しない。置き換えは新しい ADR の `supersedes` で表す。

## 原則の追記

1. ユーザーが回答の中で一般化できる理由（例:「外部公開する API は互換性を優先する」）を述べたときだけ、追記案を作る。AI の推測で一般化を足さない。
2. 追記案はラウンドの記録の最後にまとめて提示し、文言そのものの承認を求める。修正があれば修正後の文言を使う。
3. 承認された案を `docs/principles.md` に次の形で追記する。ファイルがなければ作る。

   ```
   - <原則1行>（出典: ADR-007、2026-11-15）
   ```

4. 承認されなかった案は書かず、log に `principle_rejected` の行を残す。
